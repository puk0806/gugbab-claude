# 레거시 스펙 명세 템플릿 (spec-extraction-method)

> 이 양식은 공식 표준이 아니라 `spec-extraction-method` 스킬이 자체 정의한 것이다(한국식 화면정의서 공식 표준 없음, ISO/IEC/IEEE 29148:2018은 개요만 참고).
> 대상 레포 `docs/spec/` 아래에 복사해 쓴다. 예시 값은 모두 가상이다.

---

## 0. 공통 규칙

모든 표의 모든 행에 아래 3칸을 둔다. 생략하지 않는다.

| 칸 | 허용 값 |
|------|------|
| 근거 | `파일경로:줄` (여러 개면 `;` 로 구분). 근거 없는 행은 작성 금지 |
| 확신도 | `확인됨` · `추정` · `미확인` |
| 사용 여부 | `사용` · `미사용` · `미확인` — 괄호 안에 판정 근거(예: `사용(접근로그 30일 1,204건)`, `미사용(로그 90일 0건, 담당자 확인)`) |

추가 규칙:
- 코드로 확정 못 하는 칸은 빈칸이 아니라 `미확인`.
- 의미 해석이 섞인 행은 `확신도 = 추정`.
- 근거를 다시 열어 내용이 안 맞으면 행을 지우고 `[철회: 사유]` 로 남긴다.

## 7-4. 비즈니스 규칙 — `rules/<도메인>.md`

```markdown
| 규칙ID | 서술(현행 동작 그대로) | 발생 위치(화면ID/API/SQL ID/배치ID) | 조건 | 예외 | 특성화 테스트 ID | 현행 버그 메모 | 근거 | 확신도 | 사용 여부 |
|------|------|------|------|------|------|------|------|------|------|
| BR-ORD-001 | 결제완료 상태에서만 취소 가능 | POST /orders/{id}/cancel | status=PAID | 관리자 권한은 배송중도 허용 | CT-ORD-001 | 배송중 취소 시 환불 금액에 배송비 이중 차감(현행 유지 여부 결정 대기) | | 확인됨 | 사용 |
```

작성 규칙:
- 서술은 "해야 한다"가 아니라 **"현재 ~한다"** 로 쓴다(특성화).
- 버그로 보이는 동작도 서술에 그대로 쓰고, 판단은 `현행 버그 메모` + README "결정 대기"로 넘긴다.
- 특성화 테스트가 아직 없으면 `미작성`.
