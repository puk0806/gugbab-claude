## 0. 이 스킬의 범위 — 다른 스킬과의 경계

| 질문 | 담당 |
|------|------|
| 레거시에서 **무엇을, 어떤 양식으로, 어떤 순서로** 뽑아 스펙으로 남기나 | **이 스킬** (기술 무관 공통) |
| Spring 컨트롤러·MyBatis 매퍼 XML에서 실제로 어떻게 뽑나 | `spring-mybatis-spec-extraction` (설치된 경우) |
| React 라우트·컴포넌트·API 호출에서 어떻게 뽑나 | `react-spec-extraction` (설치된 경우) |
| 넥사크로 17 `.xfdl` 구조(Dataset·Transaction·이벤트) 해부 | `nexacro-17-xfdl-anatomy` (설치된 경우) |
| 특성화 테스트·승인 테스트를 실제로 작성하는 법 | `characterization-testing` (설치된 경우) |
| 목표 구조로 코드를 **옮기는** 절차(Strangler Fig 실행, codemod, PR 분할) | `incremental-refactoring` (설치된 경우) |
| 새 시스템의 도메인 모델 설계(바운디드 컨텍스트·Aggregate) | `ddd` |

이 스킬은 **"옮기기 전에 현재 시스템이 무엇을 하는지 문서로 확정하는 단계"** 만 다룬다. 산출물은 대상 레포의 `docs/spec/` 에 둔다(관례).

## 1. 역공학의 정의 — 스펙 추출은 "재문서화 + 설계 복원"이다

Chikofsky & Cross(1990)의 분류(2차 소스 기준 인용):

| 용어 | 정의 | 스펙 추출에서의 의미 |
|------|------|------|
| **Reverse Engineering** | 대상 시스템을 분석해 (1) 구성요소와 그 상호관계를 식별하고 (2) 시스템을 다른 형태 또는 더 높은 추상 수준으로 표현하는 과정 | 전체 활동. **시스템을 바꾸지 않는다** |
| **Redocumentation** | 같은 추상 수준 안에서 의미적으로 동등한 표현을 새로 만들거나 고치는 것 | 화면·API·SQL 목록을 **있는 그대로** 표로 옮기는 일 |
| **Design Recovery** | 시스템 관찰에 도메인 지식·외부 정보·추론을 더해, 코드만 봐서는 얻을 수 없는 더 높은 추상(의미)을 식별하는 것 | "이 SQL 3개가 합쳐서 '주문 취소' 규칙이다"처럼 **의미를 붙이는** 일 |
| Forward Engineering | 상위 추상·구현 독립 설계에서 물리적 구현으로 가는 전통적 과정 | 추출된 스펙으로 **재구축**하는 다음 단계 |
| Restructuring | 외부 동작(기능·의미)을 유지한 채 같은 추상 수준에서 표현 형태를 바꾸는 것 | 이 스킬 범위 밖(`incremental-refactoring` — 설치된 경우) |
| Reengineering | 대상 시스템을 검사·변경해 새 형태로 재구성하고 구현하는 것 | 역공학 + 순공학의 합 |

> 주의: 원 논문(IEEE Software 7(1), 1990, pp.13-17)은 유료 열람이라 원문을 직접 확인하지 못했다. 위 정의는 Georgia Tech Reverse Engineering 용어집·IEEE-CS TCSE 용어집(훔볼트대 미러)·Georgia Tech 논문 요약 3개 2차 소스의 공통 내용이다. 특히 **Redocumentation의 문구는 소스마다 다르다**("같은 상대 추상 수준의 의미 동등 표현 생성·수정" vs "사람 독자를 위한 대안 뷰인 restructuring의 한 형태" vs "잃어버린 문서를 복구하는 하위 영역"). 정확한 원문 인용이 필요하면 논문을 직접 확인한다.

**실무 함의:** 재문서화(사실 나열)와 설계 복원(의미 부여)을 **같은 칸에 섞지 않는다.** 사실은 코드 근거로 "확인됨"이 되지만, 의미는 사람(도메인 전문가) 확인 전까지 "추정"이다. 이 구분이 7절 양식의 `확신도` 칸이다.

## 2. 현행 동작을 고정한다 — 특성화 테스트·승인 테스트

### 2-1. 특성화 테스트 (Characterization Test)

Feathers(2016) 원문: **"The purpose of characterization testing is to document your system's actual behavior, not check for the behavior you wish your system had."**

- "올바른 동작"을 검증하는 테스트가 **아니다.** "지금 실제로 이렇게 동작한다"를 기록·고정한다.
- 절차(Feathers 블로그): 이름 없는 테스트(`x`) 작성 → 기대값을 임의값(null)으로 → 실행해 실제 출력 확인 → 실제 출력을 단언에 넣음 → 발견한 동작에 맞게 테스트 이름 변경 → 다른 입력으로 반복.
- 용어는 Feathers의 *Working Effectively with Legacy Code*(2004)에서 유래한 것으로 널리 인용된다.

**스펙 추출에서의 역할:** 비즈니스 규칙 명세의 각 규칙은 **특성화 테스트 ID와 짝을 이룬다**(7-4). 문서 서술은 틀릴 수 있지만 통과하는 특성화 테스트는 현행 동작의 실행 가능한 증거다.

### 2-2. 승인 테스트 / 골든 마스터

- ApprovalTests: "결과의 스냅샷을 찍고, 그것이 바뀌지 않았는지 확인한다." 처음 결과를 사람이 **승인(approve)** 하고, 요구가 바뀌면 다시 승인한다.
- 골든 마스터: 기존 코드 출력을 기준 파일로 저장하고 새 코드 출력과 비교한다. 출력이 크거나 복잡한 화면·리포트·배치 결과에 유리하다.
- 특성화 테스트·승인 테스트·골든 마스터·스냅샷 테스트는 실무에서 거의 같은 의미로 섞여 쓰인다. 공통점은 **"현행 출력 = 기준"** 이다.

### 2-3. 현행 버그를 어떻게 다루나

특성화 테스트는 **버그도 그대로 고정한다.** 고치지 말고 비즈니스 규칙 명세의 `현행 버그 메모` 칸에 적고, 재구축 시 "버그 호환 유지 / 수정"을 **사람이 결정**하게 한다. Feature Parity 패턴 문서도 "과거 버그·한계를 피하려던 우회책이 현재 업무 프로세스의 필수 요구가 되어 있다"고 경고한다.

> 세부 작성법(시드 고정, 시간·난수 제어, 출력 정규화, 스크러버)은 `characterization-testing` 스킬로.

## 3. 전부 옮기지 마라 — Strangler Fig와 Feature Parity 경고

### 3-1. Strangler Fig (Fowler, 2024-08-22 개정)

새 코드베이스를 레거시 위에(하지만 분리해) 작게 붙여 나가며 **"레거시 시스템의 동작을 조각 단위로 새 코드베이스로 옮긴다."** Fowler는 같은 글에서 레거시 동작의 상당수가 "실제로는 원하지 않는 것이라 다시 만드는 건 낭비"라고 적는다. 신·구 공존용 **전이 아키텍처**가 필요하다는 점도 명시한다. (실행 절차는 `incremental-refactoring` — 설치된 경우)

### 3-2. Feature Parity 패턴 — 함정으로 알고 써라

Cartwright·Horn·Lewis(2021) 정의: **"레거시 시스템의 기존 기능을 새 기술 스택으로 복제한다."** 사용한 사람들 사이에서는 "feature parity trap"으로 불린다. Thoughtworks Radar는 "legacy migration feature parity"를 **Hold**(안티패턴)로 분류했다.

| 위험 | 원문 근거 |
|------|------|
| 노력 과소평가 | "'as is' 범위를 정의하는 것만으로도 엄청난 노력" |
| 비대한 기능 | 기능의 다수가 미사용(2014 Standish Group 보고서 인용 50%)인데 그대로 복제 |
| 박제된 우회책 | 과거 버그·한계의 우회책이 "필수" 요구가 되어 있음 |

> 주의: "미사용 기능 50%"는 Feature Parity 문서가 2014 Standish Group 보고서를 **재인용**한 수치다. 보고서 원문은 확인하지 않았다. 스펙 문서나 보고서에 인용할 때는 "재인용"임을 밝힌다.

**권고 → 스펙 양식 요구사항으로 번역:**

| 패턴 문서 권고 | 스펙에 반영하는 방법 |
|------|------|
| 접근 로그·계측으로 **실제 사용량 분석** | 모든 명세 행에 **`사용 여부` 칸 필수** (값: 사용 / 미사용 / 미확인 + 근거: 로그 기간·호출 수) |
| 메뉴·레이어 단위가 아니라 **end-to-end 업무 프로세스 단위로 진척 추적** | 화면·API·SQL을 **프로세스 ID로 묶는다**. CRUD 매트릭스의 열/행이 프로세스 |
| 비즈니스 지표로 우선순위 | 프로세스 목록에 우선순위 칸(업무 담당자가 채움) |

`사용 여부 = 미사용` 판정 행은 삭제하지 말고 남긴 채 "재구축 제외 후보"로 표시한다. 제외 여부는 사람이 결정한다.

## 4. 사람으로 검증한다 — EventStorming

EventStorming(Alberto Brandolini)은 **"복잡한 비즈니스 도메인을 협업으로 탐색하는 유연한 워크숍 형식"** 이다. 배경이 다른 이해관계자(도메인 전문가·업무 담당자·개발자) 간 대화를 끌어낸다. 널리 알려진 수준은 Big Picture(도메인 전체) / Process Level(흐름 하나) / Software Design(코드 경계) 세 가지다.

**스펙 추출에서 쓰는 법 — 코드에서 뽑은 것을 벽 위에서 검증:**

1. 코드 추출로 만든 업무 프로세스 초안을 도메인 이벤트(과거형: "주문이 취소됨")로 바꿔 시간순으로 붙인다.
2. 도메인 전문가가 **빠진 이벤트·틀린 순서·안 쓰는 이벤트**를 지적한다 → 지적은 핫스팟으로 표시.
3. 지적 결과를 스펙에 반영: 빠진 것 = 코드 재조사, 틀린 것 = `확신도`를 "추정"으로 강등하고 수정, 안 쓰는 것 = `사용 여부` 갱신.
4. 코드엔 있는데 아무도 모르는 이벤트 = Feature Parity 함정 후보(3-2).

> 주의: eventstorming.com 현재 메인은 워크숍 용도를 Improve / Envision / Explore / Design 4가지로 소개한다. "Big Picture / Process / Software Design" 3단계는 Brandolini 서적·DDD Europe 마스터클래스 등에서 쓰이는 분류다. 둘은 다른 축(용도 vs 확대 수준)이다.

## 5. 데이터 완전성 점검 — CRUD 매트릭스

CRUD 매트릭스는 **데이터(엔티티·테이블)와 프로세스를 잇는 행렬**로, 각 칸에 C/R/U/D를 적는다(DePaul 강의 자료는 행=엔티티, 열=프로세스. 축 방향은 관례 차이일 뿐).

**완전성 규칙 (Bernstein, DePaul IS 315):**

1. **"모든 엔티티는 C·R·U·D가 각각 최소 1개씩 있어야 한다. 아니면 프로세스가 하나 이상 누락됐을 수 있다."**
2. **"한 엔티티에 Create가 여러 개면 데이터 중복 문제일 수 있다."**
3. (역방향) 어떤 엔티티에도 손대지 않는 프로세스, 어떤 프로세스도 쓰지 않는 엔티티는 의심한다.

**레거시 추출에서의 해석:**

| 점검 결과 | 레거시에서 흔한 원인 | 조치 |
|------|------|------|
| C 없음 | 외부 배치·타 시스템·DB 직접 적재·초기 데이터 | 7-5 배치·연동 명세에서 찾는다. 못 찾으면 "미확인" |
| D 없음 | 논리 삭제(삭제 플래그 U), 보존 정책 | D 대신 "논리 삭제(U)"로 명시 |
| U 없음 | 이력·로그성 테이블(append-only) | 정상일 수 있음 — 사유를 메모 |
| C 다중 | 화면별 복붙 INSERT, 등록 경로 중복 | 중복 의심 표기 → 재구축 시 단일화 후보 |
| 어느 프로세스도 안 씀 | 죽은 테이블 | `사용 여부 = 미사용` 후보 |

> 주의: 규칙은 DePaul 강의 자료(2003)와 TMap 등 테스트 문헌이 같은 내용을 담고 있어 교차 확인했다. CRUD 매트릭스가 **정보공학(Information Engineering)에서 처음 도입**됐다는 기원은 2차 소스(학술 논문)의 서술이며 원 출처는 확인하지 못했다. 위 규칙은 "완전성의 단서"이지 "위반 = 오류"가 아니다.

## 6. LLM으로 대규모 코드를 추출할 때의 규약

### 6-1. 근거

- **Thoughtworks Radar**: "using GenAI to understand legacy codebases"를 2025-11 판에서 **Adopt**로 올렸다. "대규모·복잡한 시스템의 이해를 상당히 가속한다"고 평가하며, 비즈니스 규칙 도출·로직 요약·의존 식별을 용도로 든다.
- **CodeConcise(Thoughtworks)**: 코드를 **AST 숲으로 파싱해 그래프 DB에 저장**하고 노드 간 제어 이동 등 관계를 엣지로 만든 뒤, 그래프 탐색으로 **LLM에 넘길 컨텍스트에서 불필요한 코드를 줄인다**. 저자들은 "사람이 출력을 완전히 통제"하며 **SME(도메인 전문가) 접근이 레거시 이해에 필수**라고 적는다.
- **Anthropic 환각 감소 가이드**: (1) "모르겠다"고 말할 권한을 준다 (2) 긴 문서는 **원문 그대로 인용을 먼저 뽑고** 그 인용에 근거해 작업 (3) 각 주장마다 인용을 달게 하고, **지지 인용을 못 찾으면 그 주장을 철회**하게 한다 (4) 제공 자료 외 일반 지식 사용 제한. 그리고 "이 기법들은 환각을 줄이지만 없애지는 못한다. 중요한 정보는 항상 검증하라."
- **Claude Code 서브에이전트**: 각자 **독립 컨텍스트 창**에서 작업하고 **요약만 반환**한다 → 수천 파일 탐색이 메인 대화를 오염시키지 않는다.

> 주의: Radar 항목은 이후 판에서 빠질 수 있다(Radar는 판마다 항목을 교체한다). 인용 시 "2025-11 판 Adopt"로 시점을 붙인다.

### 6-2. 추출 규약 (프롬프트·서브에이전트 지시에 그대로 넣는다)

| # | 규약 | 이유 |
|---|------|------|
| R1 | **모듈(업무 단위·패키지·화면 묶음) 단위로 분할**해 서브에이전트 1개 = 모듈 1개 | 컨텍스트 창 한계, 노이즈 감소(CodeConcise와 같은 발상) |
| R2 | **모든 주장에 근거 `파일:줄` 인용** | 감사 가능성. 사람이 1클릭으로 확인 |
| R3 | 작성 후 각 행의 근거를 다시 열어 확인하고, **인용을 못 찾으면 그 행을 철회** | Anthropic "verify with citations" |
| R4 | 코드로 확정 못 하면 **"미확인"** 이라 쓰고 추측으로 채우지 않는다 | "I don't know" 허용이 거짓 정보를 줄인다 |
| R5 | 일반 지식으로 메우지 않는다 — "Spring이니까 보통 이렇다" 금지 | 외부 지식 제한 |
| R6 | 의미 해석(설계 복원)은 `확신도 = 추정`으로만 | 1절 재문서화/설계 복원 구분 |
| R7 | 서브에이전트는 **양식(7절) 그대로의 표**만 반환, 메인이 병합 | 병합 시 칸 불일치 방지 |
| R8 | 병합 후 **도메인 전문가 검토 필수**(EventStorming 또는 표 리뷰) — LLM 출력은 초안 | CodeConcise·Anthropic 모두 사람 검증을 전제 |
| R9 | 같은 모듈을 두 번 추출해 결과가 다르면 그 행은 "추정"으로 강등 | Anthropic "Best-of-N verification" |

```text
# 서브에이전트 지시 예시 (모듈 1개)
대상: <모듈 경로> 아래 파일만.
산출: docs/spec/ 양식의 "API 명세" 표 행만 반환.
규칙:
- 모든 행에 근거(파일:줄)를 단다. 근거 없는 행은 쓰지 않는다.
- 다 쓴 뒤 각 행의 근거 줄을 다시 열어 확인하고, 내용과 안 맞으면 행을 삭제하고 "[철회: 사유]"를 남긴다.
- 코드로 확정할 수 없는 칸은 "미확인"으로 둔다. 일반 관례로 추측하지 않는다.
- 의미 해석이 들어간 칸은 확신도를 "추정"으로 한다.
```

## 7. 명세 양식 — 4종 + 배치·연동

> 주의: **한국식 "화면정의서"에는 공식 표준이 없다.** 회사·프로젝트마다 항목을 가감해 쓴다(국내 기획 실무 자료들도 "구성에 정답이 없다"고 명시). ISO/IEC/IEEE 29148:2018(요구공학, 현행 표준)은 **개요만 확인**했으며, 아래 양식은 그 표준을 따른 것이 아니라 **이 스킬이 자체 정의한 것**이다.

### 7-0. 모든 행 공통 칸 (생략 금지)

| 칸 | 값 | 규칙 |
|------|------|------|
| `근거` | `path/to/File.ext:123` (복수 가능) | 없으면 행을 쓰지 않는다 (R2·R3) |
| `확신도` | **확인됨** / **추정** / **미확인** | 확인됨 = 코드 근거로 사실 확인 · 추정 = 해석·추론 포함 · 미확인 = 조사했으나 확정 불가 |
| `사용 여부` | **사용** / **미사용** / **미확인** (+ 근거: 로그 기간·호출 수·담당자 확인) | Feature Parity 함정 방지 (3-2) |

### 7-1 ~ 7-5 개요

| # | 명세 | 핵심 칸 |
|---|------|------|
| 7-1 | **화면 명세** | 화면ID·화면명·경로·권한 / 입력 필드(이름·타입·필수·기본값·검증·코드값) / 출력·그리드 컬럼 / 버튼·이벤트 → 호출 API / 화면 이동·팝업 / 메시지 |
| 7-2 | **API 명세** | 메서드+URL·핸들러 / 요청·응답 스키마 / 인증 / 에러 / 호출 화면 / 사용 SQL ID |
| 7-3 | **데이터 사용 명세** | SQL ID·C/R/U/D·테이블·컬럼·동적 조건 / CRUD 매트릭스 / 완전성 점검 |
| 7-4 | **비즈니스 규칙** | 규칙ID·서술·발생 위치·조건/예외·특성화 테스트 ID·현행 버그 메모 |
| 7-5 | **배치·외부 연동** | 배치ID·주기·트리거·입출력 테이블 / 연동 대상·방향·프로토콜·포맷·실패 처리 |

**전체 마크다운 템플릿 → [`references/spec-templates.md`](references/spec-templates.md)**

### 7-6. 명세 간 연결 키 (추적성)

```
프로세스ID ─┬─ 화면ID ── 버튼/이벤트 ── API(메서드+URL) ── SQL ID ── 테이블
            ├─ 배치ID ───────────────────────────────── SQL ID ── 테이블
            └─ 규칙ID ── 발생 위치(화면ID/API/SQL ID) ── 특성화 테스트 ID
```

- 화면 명세의 "호출 API" = API 명세의 키, API 명세의 "사용 SQL ID" = 데이터 명세의 키. **키가 한쪽에만 있으면 누락이다.**
- 모든 행은 최소 1개 프로세스ID에 속한다. 어느 프로세스에도 안 속하면 `사용 여부` 확인 대상.

### 7-7. 산출 위치 관례 (대상 레포)

```
docs/spec/
├── README.md               # 범위·프로세스 목록·진척·용어집
├── screens/<화면ID>.md     # 7-1
├── api/<도메인>.md         # 7-2
├── data/<도메인>.md        # 7-3 (+ crud-matrix.md)
├── rules/<도메인>.md       # 7-4
└── batch-integration.md    # 7-5
```

## 9. 언제 쓰고 언제 쓰지 않나

**적합:** 기술 스택 교체·재구축 전 현행 스펙이 없거나 문서가 코드와 어긋난 경우 / 외주·이관으로 지식 보유자가 떠나는 경우 / 대규모 코드를 LLM으로 빠르게 훑되 결과를 감사 가능하게 남겨야 할 때.

**부적합:** 스펙 문서가 최신이고 테스트가 충분한 시스템(검증만 하면 된다) / 단순 리팩터링(동작 불변이면 `incremental-refactoring`(설치된 경우) + 테스트로 충분) / 기능을 **새로 정의**하는 재설계(현행 복제가 목표가 아니면 사용량 분석·EventStorming만 차용).

## 10. 흔한 실수

| 실수 | 왜 문제인가 | 올바른 접근 |
|------|------|------|
| 모든 기능을 1:1 복제 대상으로 표기 | Feature Parity 함정 — 미사용 기능·우회책까지 재구축 | `사용 여부` 칸 필수, 미사용은 제외 후보로 |
| 메뉴 트리 순서로 진척 관리 | 업무 프로세스가 끝까지 옮겨졌는지 알 수 없음 | 프로세스 ID 단위 추적 |
| 특성화 테스트를 "정답 검증"으로 착각하고 버그를 고침 | 현행 동작 기록이 깨지고 업무가 의존하던 동작이 사라짐 | 버그는 메모만, 수정은 사람 결정 |
| LLM 추출물을 근거 없이 그대로 스펙 확정 | 그럴듯한 환각이 스펙에 박힘 | R2·R3: 파일:줄 인용, 못 찾으면 철회 |
| 모르는 칸을 관례로 채움 | "추정"이 "사실"로 둔갑 | "미확인" 기재 |
| 한 프롬프트에 전체 레포 투입 | 컨텍스트 초과·노이즈로 누락 | 모듈 단위 서브에이전트 |
| CRUD 위반을 무조건 오류로 판단 | 논리 삭제·외부 적재 등 정상 사례 존재 | 원인 표(5절)로 분류 후 사유 기재 |
| 재문서화와 설계 복원을 한 칸에 | 사실과 해석 구분 불가 | 확신도 칸으로 분리 |
| 도메인 전문가 검토 생략 | 코드에 없는 업무 규칙(수작업·운영 관행) 누락 | EventStorming/표 리뷰 필수 |
| 사내 "표준 화면정의서"라 믿고 항목 고정 | 공식 표준이 없음 | 이 양식을 출발점으로 프로젝트에 맞게 가감 |
