# 작업 착수 전 확인 절차

복잡한 작업(구현·설계·추가·변경·개편 등)을 시작하기 전에 반드시 아래 순서를 지킨다.

> **훅으로 강제된다 (2026-10-06 `task-confirm-guard`)**: 직전 답변의 **마지막 줄**이 "진행할까요?"이고
> 사용자가 승인해야 Write/Edit/NotebookEdit 가 허용된다. 승인 전 파일 수정은 차단된다.
> 거절·수정 요청("아니", "말고", "다시 정리" 등)이나 승인 표현 없는 되묻기는 승인이 아니다 → 계획을 고쳐 다시 묻는다.
> 사용자가 "바로 진행"·"확인 없이"라고 하면 생략된다. 메모리·계획·임시 폴더 쓰기는 항상 허용.
> (과거 task-plan-guard / confirmation-gate 는 질문 단어로 복잡도를 추측해 오탐이 많아 제거됐다 — 새 훅은 직전 대화만 본다)
> 여러 파일에 걸친 대규모 작업은 네이티브 **Plan Mode**를 써도 된다 (계획 승인 버튼은 자동 승인 — "진행할까요?"가 확인을 대신한다).

---

## 필수 순서

### 1단계: 이해 확인
"이렇게 이해했습니다:" 형식으로 요청 내용을 1-3줄로 요약한다.

### 2단계: 작업 목록 리스트업
번호 있는 구체적 단계 목록을 제시한다.

```
1. ...
2. ...
3. ...
```

### 3단계: 사용자 확인 대기
"진행할까요?" 로 확인을 요청하고 **승인 전 코드·파일 수정 금지**.
"진행할까요?"는 답변의 **마지막 줄**에 따옴표 없이 쓴다 — 본문 중간이나 인용 형태는 훅이 승인 질문으로 인정하지 않는다.

### 4단계: 승인 후 실행
---

## 예외 — 즉시 실행 가능

| 예외 유형 | 예시 |
|----------|------|
| git 커밋·푸시 | "커밋해줘", "푸시해줘" |
| 내용 요약·설명 | "요약해줘", "설명해줘", "알려줘" |
| 단순 조회 | "읽어줘", "찾아줘", "보여줘" |
| 1줄 단순 수정 | 오탈자 수정, 변수명 변경 1건 — **단, 훅은 수정 크기를 구분하지 못해 차단한다.** 사용자가 "바로 수정해"처럼 생략을 명시했을 때만 즉시 실행, 아니면 짧게라도 "진행할까요?"를 거친다 |

---

## 왜 필요한가

작업 전 확인 없이 진행하면:
- 의도와 다른 방향으로 구현될 수 있음
- 되돌리기 어려운 변경이 이미 발생한 후 방향 수정 요청이 들어옴
- 사용자가 놓친 엣지케이스를 미리 발견할 기회를 잃음
